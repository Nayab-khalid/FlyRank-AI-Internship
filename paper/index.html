Abstract

This project asks whether observable search, content and freshness signals can help a content team decide which pages to review first when review capacity is limited. The executed analysis uses the FlyRank anonymized starter dataset of 30,000 content pages and 44 source columns covering 32 pseudonymized clients, with the larger warehouse release used to verify the data contract. The task was framed as binary classification on an observed decline label and compared against a transparent staleness and visibility baseline under an 80/20 split grouped by client, and a leakage audit found the label to be exactly reconstructible from two columns in the first feature set, which were removed along with four related columns before the reported evaluation. On the same held out test rows the corrected model reached an Average Precision of 0.596008, ROC AUC of 0.594877 and Precision@50 of 0.70, against 0.489069, 0.506511 and 0.30 for the baseline, measured against a test set positive rate of 51.1 percent. The output is measured and directional decision support for prioritizing human content review, not a causal explanation of search performance and not a prediction of Google's ranking system.

1.Introduction

The decision supported by this project is which content pages a content team should review first.

A content team may have many pages but limited time. A ranked list can help the team spend its review time on pages that appear more relevant to the defined decline problem. For the executed starter dataset, one row represents one content page. The output is a score for each page, and pages can then be ranked from higher score to lower score.

A human reviewer uses the ranked queue to decide whether a page should be refreshed, protected and refreshed carefully, reviewed for click through rate, reviewed for engagement, expanded or monitored. The ranking decides what is looked at first. The reviewer decides what happens to the page.

The research question is:

Can observable search, content and freshness signals help a content team rank pages so that limited review time is focused on pages associated with an observed declining trend?

Cost of a wrong call

A false positive wastes editorial time on a page that does not need attention. A false negative causes a page that deserves review to be missed. There is also a risk of damaging a useful page if a recommendation is acted on without human review, which is why the output is designed as a queue rather than an instruction.

Machine learning is useful here because a simple rule identifies obvious cases, while many pages carry several signals at once. The model provides a way to combine multiple measurable signals into one ranking score. It is used to prioritize human review rather than to replace human judgement.

2.Data

Release used

The executed modeling work uses the FlyRank anonymized starter dataset: 30,000 content pages, 44 source columns, 32 pseudonymized clients. Every model number reported in this paper comes from that dataset.

The internship also provides a larger warehouse release of approximately 79 million daily search performance rows. The warehouse was used to write and verify the data contract, not to train the reported model. No result in this paper is presented as a result trained on all 79 million rows.

The starter dataset carries relative windows rather than calendar dates. Target definition

The target is is_declining_label, equal to 1 when trend_direction is down and 0 otherwise. The starter dataset contains 16,262 declining rows and 13,738 non declining rows, an overall positive rate of approximately 54.2 percent.

This base rate matters when reading Precision@50. A high precision score should be read next to the class distribution and the discrimination metrics, not on its own.

Public safety

The project uses anonymized data throughout. No client names, private domains, private URLs or private search queries appear in this paper, in the notebooks, or in any exported artifact. Client and content identifiers appear only in pseudonymized hashed form and are never used as model inputs.

3.Methodology

Assumptions

  • The observed decline label is a usable proxy for a page being worth a reviewer's attention. It is not a measure of future business value.
  • The signals used are observable before the review decision is made.
  • Missingness is systematic rather than random. The data dictionary states that a missing GA4 measurement does not mean zero engagement, so missing values are imputed rather than zero filled.
  • The data is observational, so no part of this design can establish causation.

Label definition

A page is labelled positive when its documented trend_direction is down within the starter dataset's observation window.

Baseline

The Week 4 baseline is a transparent rule based score, written before any model was trained. A page is prioritized for refresh review when it is both stale, meaning at least 180 days since the last update, and visible, meaning at least 500 search impressions in the 90 day window. The score combines staleness and visibility points so that older and more visible pages rank higher.

The baseline emits the reason code stale_visible_page and the action REVIEW_REFRESH. It uses no label field and no future window data, and it is scored on exactly the same held out test rows as the model, which is what makes the comparison fair.

Features

The first feature vector held 26 features: 23 numeric and 3 categorical. The leakage audit below removed six of them. The final vector holds 20 features: 17 numeric and 3 categorical.

Table 4. Final feature set.

Numeric missing values are median imputed. Categorical missing values are filled with an explicit unknown category rather than dropped. The largest single gap is word_count, missing on 7,699 of 30,000 rows, which is one reason content length is treated as weak evidence in the recommendations.

Model choice

Logistic Regression was selected for the main model. The target has two possible outcomes, the model produces a probability that can be used directly to rank pages, and its coefficients are relatively easy to interpret compared with more complex models. For a ranking that a reviewer has to trust and question, interpretability was weighted above raw fit.

Validation design

An 80 percent training and 20 percent test split, grouped by client, with random seed 42.

Leakage and privacy checks

The leakage hunt was run three times. The first two passes, in Week 3 and Week 6, checked whether any forbidden column appeared in the feature list by name. Both reported zero forbidden fields. The third pass, run while preparing this paper, tested something different and did not pass.

Table 6. Leakage and privacy audit, all three passes.
CheckResult
Forbidden label derived fields present by name0 found, PASS
Target used as a featureNo, PASS
trend_direction or trend_pct used as featuresNo, PASS
Suspicious feature namesNone, PASS
Identifier fields used as featuresNone, PASS
Any single feature with standalone AUC above 0.95None, PASS
Label reconstructible from the feature setExactly, on all 30,000 rows. FAIL

The name based checks cannot detect a label rebuilt from columns that are individually permitted. The data dictionary defines the label as a comparison of two windows:

trend_pct       = (impressions_last_30d - impressions_prev_30d)
                  / impressions_prev_30d * 100
trend_direction = "down" when trend_pct < -20
label           = 1 when trend_direction == "down"

Both impressions_last_30d and impressions_prev_30d were in the feature set. Excluding trend_pct by name while supplying the two columns it is computed from leaves the label fully available to the model. Applying the documented formula directly to those two features reproduces the label on every row:

documented rule vs label agreement: 1.000000
positives predicted: 16,262    actual: 16,262

The clicks and sessions versions of the same two windows were removed as well. They are not the label by definition, but their ratio tracks the impression ratio closely enough to approximate it. Section 4 reports what the removal cost.

Two checks were added so that this class of problem is caught by the audit rather than by a reader. The first applies each documented label formula to the surviving feature set and measures agreement. The second trains a random forest probe on the features alone and reports its cross validated accuracy: a probe that reaches near perfect accuracy on a task where a rule baseline sits at chance is reading the answer rather than learning it. On the 23 numeric features the probe reached 0.9122; on the 17 that remain it reaches 0.6994, against a base rate of 0.542.

One risk is still not closed. The surviving 90 day aggregates and the rates derived from them cover a window that contains the 30 days the label is measured over, so they are contemporaneous with the outcome rather than prior to it. This is consistent with what the paper claims, which is association with an observed label rather than prediction of a future one, but it is not the same as a clean forecasting setup. Section 6 states the consequence, and any future window variable that overlaps the outcome period must be excluded when this work moves to the warehouse.

4.Results

The model and the baseline were scored on the same held out test rows, with the same metrics, under the same client grouped split. The model reported here is the corrected one, trained on the 20 features that survived the leakage audit.

Table 7. Baseline and Logistic Regression on the same held out test rows.
Metric Baseline Logistic Regression Change
Average Precision 0.489069 0.596008 +0.106939
ROC AUC 0.506511 0.594877 +0.088366
Precision@50 0.30 0.70 +0.40
Test set positive rate 51.1% across 6,163 test rows and 7 held out clients

The model ranks better than the baseline on all three metrics, and the margin is modest. Average Precision rises by about a tenth. ROC AUC of 0.594877 describes a ranking with real but limited discrimination. Precision@50 of 0.70 sits 0.19 above the 51.1 percent test base rate, so the top of the queue is better than an arbitrary selection without being close to reliable.

The baseline's ROC AUC of 0.506511 is close to 0.5, the level expected from a ranking with no discrimination. On these held out clients the staleness and visibility rule ordered pages barely better than chance.

The result before the leak was removed

This evaluation was first run on the 26 feature set described in Section 3, and produced much stronger numbers. They are reported here because the difference between them is the finding, not a discarded draft.

Table 8. The same evaluation before and after the six label derived features were removed.
Metric 26 features 20 features Baseline
Average Precision 0.871535 0.596008 0.489069
ROC AUC 0.849583 0.594877 0.506511

An Average Precision of 0.8715 and a Precision@50 of 1.00 were the original headline results of this project. They were produced by a model that had been given the two columns the label is computed from. Of the 0.382 gap between the baseline and the 26 feature model, 0.276 disappears when those columns are removed. The remaining 0.107 is what the observable signals contribute.

Precision@50 of 1.00 was the clearest warning sign in hindsight. A perfect top 50 against a 51.1 percent base rate, produced by a linear model, next to a baseline sitting at chance, is a pattern that should prompt an audit rather than a conclusion.

Effect of the validation design

The Week 6 audit re-ran the model under an ordinary row based split to measure what the grouped split costs. Both feature sets are shown, because the leak changed the size of the gap.

Performance drops when client overlap is removed, which is the expected direction. Part of the row based result comes from the model recognizing clients it has already seen. The gap is larger on the corrected feature set than on the original one. Once the model can no longer read the label directly, more of what remains is client specific pattern rather than general signal.

Error analysis

The ranking was inspected directly, because a metric table does not show what the mistakes look like.

Table 9. Precision at several queue depths, corrected model.
Queue depthPrecisionLift over base rate
Top 200.80+0.29
Top 500.70+0.19

Top 5000.67+0.16

Precision decays with depth and then flattens, which is the shape a working ranking produces. The practical reading is that the first 20 to 50 rows are worth a reviewer's time and the advantage thins below that.

The top 50 draws from only 2 of the 7 held out clients, and all ten of the highest scoring false positives come from one client. The ranking concentrates on whichever clients happen to match the pattern it learned, so a per client cap on the review queue would be sensible in practice.

Seven of those ten false positives are labelled up rather than stable. Their median is 759 impressions across 82.5 days with impressions, so the model is placing steady, well established pages near the top regardless of which direction they moved. It is responding to activity, not to direction.

The lowest scoring false negatives are low volume pages, with a median of 69 impressions and zero clicks over 90 days. At that volume the rate based signals are computed on almost nothing and are unstable by construction. One page in that group had 309,192 impressions, so volume alone does not explain every miss.

5.Interpretation

Once the label derived columns were removed, the corrected model found a modest amount of usable information in combinations of search performance, content and engagement signals. The Week 4 signal audit shows why the remaining signal is weak: tested one at a time, each candidate signal returned a MIXED verdict.

Note on the freshness result

The flag linked freshness test was recorded as CONFIRMED on the comparison between the newest group at 51.14 percent and the oldest group at 60.00 percent. That oldest group contains 5 pages. The 181 to 365 day group, which holds 169 pages, declines less often at 46.7 percent than the newest group does.

The defensible reading is narrower than the verdict label suggests. The well populated middle groups, 31 to 90 days and 91 to 180 days, do show a higher observed decline rate than the newest group. The sparse tail groups should not be used as evidence in either direction.

What the audit means

No single signal was strong enough to serve as a complete rule on its own, and two of the three are not monotonic. The baseline commits to older and more visible as a single direction, while the observed decline rate does not follow that direction cleanly at either end of the range. That is why a combining model ranks better than a two signal rule, and also why the margin is small: there is not much clean signal for it to combine.

The model's advantage is a ranking advantage on this population. It is not evidence that any one of these signals is a reliable standalone flag.

The pattern is coverage rather than freshness. The strongest term is the number of days a page recorded impressions, followed by the number of days it recorded sessions in the opposite direction. Pages that appear in search on many days but convert that into sessions on few days are pushed toward the decline label. This is consistent with the error analysis, where the highest scoring false positives were steady, well established pages that happened to be moving up rather than down.

Notably, days_since_last_update does not appear among the largest coefficients, even though staleness is the premise of the refresh lane. Two content size measures, word_count and char_count, carry opposite signs, which usually indicates the model is using their difference rather than either one meaningfully. Neither should be read as a finding about content length.

Negative and unexpected results

  • The project's headline result was an artifact. Average Precision of 0.8715 and Precision@50 of 1.00 came from features that encode the label, and both fell substantially once those features were removed.
  • The transparent baseline scored ROC AUC 0.506511, close to no discrimination on the held out clients. A rule that sounds reasonable did not order these pages usefully.
  • Pages ranked in the top 3 search positions decline least often, at 24.6 percent against the 54.2 percent overall rate. Visibility and decline are not the same thing.
  • The freshness signal that motivates the refresh lane came back MIXED rather than clean once group sizes were taken into account, and freshness does not appear among the corrected model's strongest coefficients either.

What this does and does not tell us

The model can help rank pages associated with the observed decline label. It does not tell us why a page declined, it does not tell us that a content change will improve performance, and it does not predict Google's ranking algorithm. The result is a prioritization signal.

6.Limitations and Honest Framing

This study has several important limitations.

  • The target is an observed decline label, not a direct future outcome. It records that a page's documented trend was down in the observation window. It does not say the page will underperform in a later period.
  • The data is observational, so the project cannot prove that a content change causes search performance to improve.
  • Seasonality, demand, competition, consolidation and cannibalization can all affect search performance and can resemble content decline.
  • Low traffic volume makes percentage based signals unstable, which appears directly in the false negative analysis.
  • Client history is not evenly distributed, and Search Console and Analytics availability differ across clients and time periods. In the verified March 2026 window, GA4 was available on 413,966 of 9,841,378 rows.
  • word_count is missing on 7,699 of 30,000 starter rows, so content length evidence is thinner than the feature list suggests.
  • The freshness verdict rests partly on groups of 169 and 5 pages, as described in Section 5.
  • Model performance may change when the population or time period changes. Precision@50 of 0.70 is a measurement on 50 pages drawn from 7 held out clients, not a guarantee.
  • The model was evaluated once under this design. There is no sealed or pre registered holdout, so the result is a validation estimate rather than a blind single shot evaluation.
  • The features are contemporaneous with the label rather than prior to it. The surviving 90 day aggregates and the rates derived from them cover a window that contains the 30 days the label is measured over, so this is an association study and not a forecast. A genuine prediction task would use a past window for features and a later window for the outcome.
  • The corrected result is modest. ROC AUC of 0.594877 is much closer to chance than to a dependable ranking, and precision falls to 0.67 by the hundredth row. The queue is useful at the top and thin below it.
  • The first two leakage audits passed while the label was fully reconstructible from the feature set. Audits that check column names cannot certify a feature set, and the checks added in Section 3 should be treated as a minimum rather than a guarantee that nothing else remains.

The appropriate claim is:

In this dataset, Logistic Regression showed measured and directional ability to rank pages associated with the observed decline label. The output is intended as decision support for prioritizing human content review. It is not a prediction of Google's ranking system and it does not establish why a page declined.

7.Ranked Recommendations

The final output is a human reviewed action queue covering all 30,000 pages. Each row carries a rank, a recommended action, the reason codes behind it, and a confidence level.

What ranks this queue

The Week 7 queue is ordered by a transparent observable signal action score, weighted 40 percent log scaled visibility, 30 percent freshness, 25 percent search position and 5 percent content depth. It is not ordered by the Logistic Regression probability.

The queue is the reviewer facing artifact, built from observable signals in a form a person can audit line by line. Section 4 measures how much ranking information signals of this kind carry once the label derived columns are removed, and the answer is a modest amount. Connecting the corrected model score to the queue ranking is the next step and has not been done yet. On the evidence in Section 4 it should be expected to help at the top of the queue and little below it.

How a reviewer would use this

  1. Work the high confidence Refresh and Protect and refresh rows first, where visibility, staleness and evidence overlap.
  2. Read the reason codes before opening the page. They record what the score responded to.
  3. Check the page against the reason. Is the information genuinely out of date, or did demand simply move?
  4. Treat the largest and smallest traffic pages with extra care, following the error analysis in Section 4.
  5. Leave low confidence rows alone unless there was already a human reason to look at them.

Human review requirements

Every high ranked recommendation must be reviewed by a person before action. The reviewer should consider the actual page content, current information, search intent, current search result context, seasonality, traffic volume, possible competing pages, strategic importance, and whether the proposed change could damage existing performance.

The system must never automatically publish content, delete or prune pages, merge URLs, change canonical decisions, rewrite metadata or important pages without human review, claim that an edit will cause recovery, treat a model probability as a causal probability, or override an experienced reviewer only because a score is high.

The model ranks the work. A human decides what should happen.

Confidence and monitoring

Confidence in the ranking rests on the measured improvement over the baseline on the evaluated test set, and it stops at the edge of the evaluated population and validation design. The queue is decision support, not an instruction list.

These are practical triggers rather than validated thresholds.

8.Reproducibility

Settings

  • Random seed: 42.
  • Validation design: 80 percent train and 20 percent test, grouped by client_id, with zero client overlap, using GroupShuffleSplit.
  • Both the baseline and Logistic Regression are scored on the same held out test rows.
  • Feature list: the 20 features in Table 4, with the six recent window columns removed. Supplying all 26 reproduces the pre correction numbers in Table 8.
  • Environment: requirements.txt in the repository root. The notebooks also run in Colab, where each one fetches the anonymized starter CSV if it is not already present.

Re-running from a fresh clone

git clone https://github.com/Nayab-khalid/FlyRank-AI-Internship.git
cd FlyRank-AI-Internship
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
jupyter lab work/notebooks/

Run the weekly notebooks in order, w01 through w07. The data contract, baseline, signal audit, split design and action queue reported in this paper come from those runs unchanged.

Which numbers came from where

The model results in Section 4 do not come from w05_model.ipynb as it currently stands in the repository. That notebook trains on all 26 features and produces the pre correction numbers shown in Table 8. The corrected numbers were produced by re-running the same pipeline, seed and split with the six recent window columns removed from numeric_features.

Everything else about the pipeline is unchanged: the same imputation, scaling, one hot encoding, class_weight="balanced" Logistic Regression, the same GroupShuffleSplit with seed 42, and the same recreation of the Week 4 baseline on the same test rows. Re-running the published notebook reproduces Table 8 exactly, which is how the correction was verified. The notebooks should be updated to the corrected feature list so that a fresh clone reproduces Section 4 directly.

Two pipelines in this repository

scripts/run_all.py is the bundled starter pipeline shipped with the internship template. It writes its own outputs/model_report.md with different figures, selecting a random forest and reporting a lower Logistic Regression result on its own split.

The analysis in this paper is the one under work/notebooks/. Where the two disagree, this paper follows the notebooks, and the bundled report should not be read as a re-run of it.
